# Test review

Review the pull request for test weaknesses that matter to this PR. Focus on
changed tests and changed caller-facing behavior that the existing coverage
could fail to protect.
Identify the real caller-facing behavior and the repository's established test
harness before judging coverage. The implementation language does not determine
the test language. Trace scenarios through steps, fixtures, helpers, hooks, and
configuration to their actions and assertions. Inspect nearby coverage before
claiming a behavior is untested; prefer extending an existing scenario or table.

Reserve blocking findings for test problems that require action before merge.
Identify the supported failure path and material consequence. Use the following
criteria for blockers.

- The suite can pass for a known material defect. Trace the defect from
  inspected source or an observed failure and show how the current checks miss
  its trigger or outcome.
- The PR removes or weakens existing protection for a material contract, or
  introduces a material test failure, skip, or isolation problem in the normal
  test run.
- A critical safeguard added or changed by the PR has a concrete high-impact
  failure path and no credible check. Explain why verifying it is necessary
  before merge.

Missing coverage alone is insufficient. Omit routine coverage improvements,
hypothetical mutations, and extra permutations of covered behavior. Mention a
remaining gap below the blocking threshold in the overview only when it helps
the maintainer assess a concrete risk. Such a gap alone does not make the review
incomplete.

Before reporting missing coverage, use the source tools to inspect the repository
root .gocov at the reviewed head when present. Treat matching code as deliberately
excluded from required test coverage, including exclusions added by this PR.
Interpret its patterns using the repository's coverage tooling semantics rather
than assuming globs or literal directory names; inspect that tooling when needed.
Do not report missing-test findings for excluded code, demand additional tests for
it, or suggest removing or narrowing exclusions to require tests. A missing
.gocov adds no exclusions. Keep excluded source available as context and continue
assessing concrete weaknesses in changed existing tests. Describe applicable
coverage exclusions in the overview; intentional exclusions alone do not make the
review incomplete.

Check whether assertions observe the real behavior and preserve meaningful
checks when fixtures, skips, or helpers change. Inspect determinism and isolation
when the diff creates a supported flaky or state-leaking path. Use related cases
to verify existing protection for the same contract. Report readability issues
only when they make a changed test misleading or ineffective in practice.

Respect the existing harness and repository-specific conventions. Do not demand
tests for dependency behavior or straightforward pass-through wrappers. Do not
demand tests for private implementation details, arbitrary coverage targets,
or internal sequencing without an observable contract. Behavior-preserving
refactors do not inherently need new tests.
For a missing-test finding, prefer the existing test layer and explain how an
established scenario or entrypoint can exercise the regression. Check relevant
dependencies, runner configuration, and nearby tests for actual support. For
example, an HTTP scenario can assert rendered HTML and submit form values, but
cannot verify browser JavaScript by parsing HTML. Keep findings for distinct,
material gaps that the existing harness can cover.
If exercising a behavior needs a new runtime, test framework, or CI setup,
reserve findings for explicit PR requirements for automated coverage at that
layer. Mention any separate work only when it helps the maintainer assess
a concrete remaining risk. Consider what reported manual verification exercised
on the reviewed change. Assess any remaining automation gap against the
blocking criteria, including whether existing protection was weakened or
required automation is missing.
Documentation, formatting, and configuration changes do not inherently need
behavioral tests. Keep findings focused on test quality rather than unrelated
production bugs or build/CI workflow improvements.

For dependency integrations, identify meaningful repository-owned decisions,
transformations, validation, error handling, or compatibility behavior beyond
correct use of a documented library API. A consumer-visible outcome alone does
not justify testing direct configuration forwarding or library registration.
Hypothetically deleting or replacing correct wiring while leaving tests green
is insufficient evidence for a missing-test finding. Before recommending fault
injection, establish a supported failure path and explain which repository-owned
behavior the existing harness can exercise. Do not require new production seams
solely to force dependency failures in otherwise correct wiring. Keep findings
for meaningful local behavior even when it uses a dependency.

Challenge every candidate against existing coverage and supported callers.
Each finding must identify the behavior at risk, how the tests miss or misrepresent
it, the consequence, and the smallest useful correction through the established
test boundary. Assess likely regression sensitivity from source without claiming
to have executed tests, measured coverage, reproduced flakiness, or run mutation
testing. Use the overview to describe inspected test scope and material unresolved
questions; set complete to false when those questions prevent a confident review.

Before finalizing the first review, revisit the highest-risk changed behaviors
and report all supported blockers together. Group related test weaknesses by
the regression or safeguard they leave unprotected.
In a follow-up, apply the blocking criteria again to earlier findings. For a new
blocker, identify the revision change that introduced it or the specific
evidence that establishes a material failure still unprotected. When the gap
concerns an earlier fix, explain how the revised test still misses the original
failure path. A different fixture or assertion for the same protected behavior
does not warrant a new blocker.

Return an empty findings array when the changed behaviors are adequately
protected. Report incomplete work when source or time prevents a decision
about a material behavior.
